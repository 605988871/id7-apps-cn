# 转向影像 / Turn View

打转向灯时，把**那一侧的摄像头**画面放到仪表盘中间的地图区域：左转看左侧，右转看右侧。灯灭后
（可设 0–8 秒的延迟）自动收起，地图回来。

> 实验功能。车载摄像头在**行车中**是否愿意只给一个应用单侧画面，只有车能回答——这一版把
> 所有可能的请求方式都做成设置，并把摄像头控制单元（ECU）的答复原样印在状态页上。第一次
> 上车请从"诊断"页看结论，而不是从"画面不出来"猜原因。

## 它是怎么工作的

```
转向灯  de.bmw.body.Light.StatusFunctionsIndicators
   │   （本车已实车验证的字段，环境灯应用读的是同一个）
   ▼
camreq.js    SOME/IP：ICAM2Proxy.clientAttach({type: CLIENT_INDIRECT})
   │                 然后 changeState({application, mode: MODE_MOSAIK, perspective})
   ▼
摄像头 ECU 把 H.264 推到 AVB 媒体总线（media_transport.avb_streaming.1）
   │
   ▼
turn-cam    以接收方的身份接进这条流，拆 RTP（单 NAL / STAP-A / FU-A）成 Annex B
   │         → /dev/shm/turn-view/h264.sock
   ▼
turn-decode 用主机自己的 MSDK 解码，缩放到 1088×480 的 4:2:0 atlas
   │         → /dev/shm/turn-view/live.sock
   ▼
main.js     建一个 video 层（target = map，就是地图那一块），把帧交给它
   │         → /dev/shm/cluster-render/render.sock
   ▼
cluster-render → 仪表盘的 GPU
```

分工的理由：**请求**必须用 SOME/IP 代理，而代理只有应用进程里才有；**收流和解码**只能在 C 里
做（每秒十几帧 1088×480 的 YUV，JS 搬不动）。两半之间只有一个 socket，各自可以单独重启。

## 和参考实现（IterioDev/car-apps 的 turn-view）的关系

那一版只做**前摄像头**：它的 `mgu-camcluster` 只有 `--camera front|rear`，`perspective` 也只
求 1、5、7 这几个"含前摄"的组合，并且把 `SIDEVIEW` 当作"泊车视图占着摄像头"要避让。所以左右
侧视在这条路上拿不到，本应用是重写的：请求留在 JS 里（可配置），接收换成自己的 `turn-cam`，
解码复用那份已经在车上跑通的 `decode.c`（现在放在 `kit/turn-cam/src`，用 `--dir` 跑在自己的
目录里）。

## 设置

| 设置 | 说明 |
|---|---|
| 显示在 | 仪表盘中间 / 关闭。关闭时应用仍在读转向灯，只是不建图层 |
| 什么时候显示 | 左转和右转 / 只左转 / 只右转 / 双闪。双闪取 `WARNBLINKEN*`、`CRASH_BLINKEN` 等 |
| 看哪一路 | 那一侧的摄像头（侧视）/ 前 / 后 / 全部（画面分割） |
| 请求方式 | `SIDEVIEW`（泊车侧视）或 `DR_ACTIVE`（行车记录视角）。侧视在**行车中**可能被拒，拒了状态页会写 |
| 左侧 / 右侧视角编号 | 侧视用的 `perspective` 数字。默认 1 / 2；第一次上车按状态页的答复调整 |
| 灯灭后再显示 | 0–8 秒。转向灯回位后画面还留一会儿，变道时不用盯着看它消失 |
| 帧率 | 5–30。摄像头本身就是 15–20 帧，调高只是多搬几次 |
| 画面缩放 / 左右上下微调 | 画面比地图区域更宽或更窄时用；100–200 %，像素级平移 |
| 常开（不等转向灯） | 不接转向灯，一直显示。**第一次上车最有用**：停在原地先确认能不能拿到画面 |

## 上车验证顺序

第一次建议照这个顺序，每一步都有可读的结论：

1. **停好车，打开"常开"**，进应用 →"诊断"页。`CameraProxy / ICAM2Proxy` 两行应为 `ok`。
   若是 `ERR ...`，是权限或服务没起来（`app.json` 已把两个代理声明为 `*`）。
2. 看 `ECU 当前`一行：这就是摄像头 ECU 自己报的状态（`application / mode / perspective`）。
   如果它一直不变，说明 `changeState` 没被接受，`请求状态`一行会写 `refused` 加原因。
3. 看 `取流`一行：`packets:` 为 0 说明 AVB 上没有流（ECU 没在推）或流名不是
   `media_transport.avb_streaming.1`（可以在 `turn-cam.service` 里加 `--stream <名字>`）。
4. 有包但没画面：看 `解码`一行和 `帧`一行。`收到 0` 说明解码器没在出帧，通常是
   `/dev/shm/turn-view-decode.txt` 里的原因（crop、MSDK）。
5. 都能走了，关掉"常开"，改回"左转和右转"，在安全的地方打一次转向灯。

`packets` 在涨但 `Frame` 一直是 0，最可能的是 RTP 拆包或解码器对不上：`turn-cam.txt` 里的
`not RTP/H.264` 和 `drops` 会说明是前者。

## 状态页读法

| 行 | 含义 |
|---|---|
| 转向灯 | 应用当前认定的转向灯状态（`左转` / `右转` / `双闪` / `没有打灯`） |
| 画面 | `显示中` / `等待转向灯` / `已关闭` |
| 请求 | 请求的 `application/perspective` 与请求状态（`asked` / `on` / `refused`） |
| 摄像头 | ECU 自己报的状态；`还没有读到状态` 表示 getter 还没返回 |
| 图层 | `hidden` / `shown` / `idle` / `refused` + 渲染器后端 |
| 帧 | 从解码器收到多少帧，交给仪表多少帧 |
| 取流 | 画面源连接状态 |
| Camera / Decode | 两个工具各自写下的报告（`/dev/shm/turn-view/turn-cam.txt`、`/dev/shm/turn-view-decode.txt`） |

## 需要装什么

| 组件 | 作用 |
|---|---|
| `idrive7-renderd` ≥ 2.1.15 | 应用自己的 GPU 渲染器（与 MGU Store 的渲染器并存） |
| `turn-cam` | 取流 + 解码两个程序，随应用一同安装；含 `turn-cam` / `turn-decode` 两个服务 |

不需要别的取流组件：解码器是从 `kit/turn-cam/src/decode.c` 编进 `turn-cam` 的，用 `--dir`
在自己的目录里跑。

## 已知边界

- **行车中的单侧视角**：`SIDEVIEW` 在原厂逻辑里是泊车功能。ECU 在行驶中可能直接拒绝，或
  只给合成画面（`MODE_MOSAIK`）。这一版能做的是把请求发出去、把答复写清楚；如果 ECU 拒了，
  "看哪一路"里选"全部摄像头"仍然能拿到含左右两块画面的一张图（再靠"画面缩放/微调"取那一块，
  精度有限）。
- **和行车记录仪的关系**：应用在收起时会 `clientDetach`，把摄像头还给行车记录仪或原厂视图；
  常开时相当于一直占着一个客户端，和行车记录仪的 DR 模式会互相顶。
- **别的应用也在用这个位置**：每个应用各有一个解码器进程、各自的 `/dev/shm/<名字>` 目录，
  互不干扰；但**地图区只有一个**，都是 `contend:1` 的内容层，谁在上取决于服务仲裁——同时
  显示时会互相顶掉，而且车机能容纳的视频层只有两个。要么关掉其中一个，要么把那个应用的
  "显示在"设为关闭。
- **地图区是抢来的**：原厂地图拿着这个位置，第三方内容层第一次争抢约有三分之一的概率失败，
  服务自己按 2/5/10/20/30 秒重试。本应用在失败后每 3 秒问一次，状态页的"图层"一行会写
  `refused`，所以"打了灯没反应"先看这一行，而不是怀疑摄像头。
- **上传预算**：整台机器所有客户端合计的带宽是有限的。1088×480 的整幅画面每秒变化时，
  15 fps 已经接近上限；和别的应用同时推流时如果画面卡顿，把"帧率"降到 10 试。
